# Үш студенттің бір-біріне кедергі келтірмей жұмыс істеуі

Бір ортақ репозиторий; әр студент өзінің жұмыс тармағында. Логиндер қажет емес:
1/2/3-студенттің орнына өз есімдеріңізді README-ге кейін жазыңыз.
GitHub-ты өздеріңіз басқарасыздар. Бұл файл — жұмыс жоспары, автоматты жариялау жасамайды.

## Негізгі қағида

**Бір файлдың бір тұрақты иесі болады.** 2/3-студент `domain.py` файлын өзгертпейді:
олар дайын модельдерді импорттайды. Өзгеріс қажет болса, файл иесіне нақты ұсыныс береді.
Әр студент өз модулінің кодын, тестін және түсіндірмесін бірге қарайды.
Үлесті барлық зертханада дәл бірдей ету үшін бір файлды бірнеше адамға беру қажет емес.

| Студент | Өзінің файлдары | Нақты жұмыс және қорғау |
|---|---|---|
| 1 | core/domain.py, core/transforms.py, data/*, app/common.py, app/overview.py, app/data.py, tests/test_lab1.py | Seed, immutable модельдер, таза түрлендіру, үш closure, баланс, деректер беті |
| 2 | core/recursion.py, core/memo.py, app/pipelines.py, app/reports.py, tests/test_lab2.py, tests/test_lab3.py | Екі рекурсия, айлық болжам, кэш өлшеу, сүзгі және есеп беттері |
| 3 | core/ftypes.py, core/validation.py, app/main.py, app/functional.py, tests/conftest.py, tests/test_lab4.py, tests/test_ui.py | Maybe/Either, толық валидация, мәзірді қосу, UI интеграциясы және қате сценарийлер |

Ортақ баптаулар мен README-ге соңғы түзетуді 3-студент енгізеді;
1-студент іске қосу нұсқауын, 2-студент есеп ережесін тексереді.
Бұл бөлу шамамен тең: 1-студентте негіз бен деректер, 2-де есептеулер мен екі тест тобы,
3-де контейнерлер, көп қате сценарийі және UI интеграциясы.

## Алдын ала бекітілген келісімдер

Барлық модель атаулары мен өрістері PDF-тегідей. Транзакциядағы өріс `cat_id`.
Барлық жинақ — tuple. 1-студент негізді бекіткен соң басқалар тек импорттайды.

```python
load_seed(path) -> (accounts, categories, transactions, budgets)
by_category(cat_id) -> predicate(Transaction) -> bool
by_date_range(start, end) -> predicate(Transaction) -> bool
by_amount_range(min, max) -> predicate(Transaction) -> bool
flatten_categories(cats, root) -> tuple[Category, ...]
sum_expenses_recursive(cats, trans, root_id) -> int
forecast_expenses(cat_id, trans, period) -> int
validate_transaction(t, accs, cats) -> Either
check_budget(b, trans, anchor=None) -> Either
validate_pipeline(t, accs, cats, budgets, trans) -> Either
```

Әр UI модулі `render(...)` береді. `main.py` тек оларды шақырады.
Жаңа өріс немесе қолтаңба туралы шешімнен кейін файл иесі өзгертеді,
қалғандары өз файлдарындағы шақыруды жаңартады. Бір адам өзгенің файлын үнсіз өзгертпейді.

## Жұмыс реті

1. 1-студент модель/seed/№1 түрлендірулерді бекітеді; 3-студент қаңқаны байланыстырады.
   2-студент шағын fixture арқылы рекурсияны дайындай алады.
2. №1 біріктірілгеннен кейін 1-студент closure келісімдерін береді,
   2-студент №2 сүзгі/рекурсия UI-ін аяқтайды. 3-студент №4 контейнерлерін жеке жасайды.
3. №2 өткен соң 2-студент кэш пен timing-ті аяқтайды;
   1-студент айлық орташа нәтижені қолмен салыстырады, 3-студент мәзірді тексереді.
4. №3 өткен соң 3-студент валидацияны байланыстырады;
   2-студент Reports бюджет кестесін, 1-студент деректер/баланс өзгерісін тексереді.
5. Әр кезеңде барлық тесттер және black/ruff орындалады. Кезең жетекшісі бір lab PR ашады,
   қалған екі студент қарап, өз тексеру нәтижесін жазады. Жетекшілер: №1 — 1,
   №2 — 2, №3 — 2, №4 — 3. 1-студент қорытынды ZIP пен іске қосуды тексереді.

## Тармақтардың қарапайым схемасы

Топтағы жеке жұмыс тармақтары: `student-1`, `student-2`, `student-3`.
Тапсыру тармақтары: `lab-01`, `lab-02`, `lab-03`, `lab-04`.
Жұмыс тармақтарынан кодты кезең жетекшісі жинайды; студенттер күнделікті өзгерістерді
`main` тармағына тікелей жазбайды. Жаңа lab тармағы **алдыңғы PR біріктірілген main-нан** басталады.
Бір lab-ты екі түрлі тармақтан қатар біріктірмеңіз. Merge conflict болса, файл иесі шешеді.

Дайын архивті пайдаланғанда әр студент өзінің түсіндіру, түзету және тест тексерулерін
нақты үлес ретінде README-ге жазады.
